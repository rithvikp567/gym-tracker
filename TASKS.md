## 1. What this is

A personal lift tracker that replaces a Google Sheet. The same exercises are kept for months or years, so the core job is **logging sets, reps, and weight per workout day and seeing how they trend over weeks, months, and years**. Mobile-first (logging at the gym), with a real desktop layout for studying trends.

Workout days: **Upper 1, Lower, Upper 2, Abs/Cardio**. Weekly split:

| Mon | Tue | Wed | Thu | Fri | Sat | Sun |
| --- | --- | --- | --- | --- | --- | --- |
| Upper 1 | Lower | Rest | Upper 2 | Lower | Rest | Rest |

Abs/Cardio happens on at least 2 rest days (any of them), so it stays off the split. Cardio is done / not done; abs exercises are weight × reps like the other days.

### How the old sheet was laid out (from the real export, tab "Upper Lower")

- Month blocks tiled 3 across × 4 down (Feb–Dec 2026; December's block has no month label, Feb's has no WEEK headers).
- Each month has 4 week column groups of **[exercise, weight, reps per set]**, e.g. `160 | 10/10` = 2 sets of 10 at 160. Sets are implied by the reps.
- Inside a week, workout days are stacked: a title row ("Upper 1") after a blank row, then one row per exercise. Target sets sometimes appear in the name: `pulldown (2)`.
- Abs/Cardio holds **two sessions a week** (Cardio 1 + abs, Cardio 2 + abs). There is a single "Lower" per week.
- Two older tabs (`Sheet1`, `Sheet2`) are 2022–2023 push/pull logs in different layouts; not imported (backlog).

### 3.2 Backend — Supabase (confirmed)

Why Supabase: relational data, built-in auth, row-level security, storage for photos later, and it fits multi-user and competition rooms (backlog a, h). Full walkthrough: [docs/SUPABASE_SETUP.md](docs/SUPABASE_SETUP.md).

- [ ] Social ([docs/SOCIAL_SETUP.md](docs/SOCIAL_SETUP.md)): run `supabase/migrations/0002_social.sql`, sign-ups back on, Gmail SMTP, the reset-code email template

Schema: tables `workout_days`, `sessions`, `splits`, each row = one app record as JSON (`data`) + `user_id`, `updated_at`, `deleted`, `server_updated_at`. A trigger keeps the newest copy when an offline device uploads an older one, and stamps server time for "what changed since". RLS: `auth.uid() = user_id`. Preferences (color style…) live in the user's auth metadata under `gym_tracker_prefs`, not a table (D20).

Social (`0002_social.sql`, D53): `profiles` (id, unique username, display name; never an email), `friendships` (requester, addressee, pending / accepted; one row per pair), `rooms` (name, owner), `room_members` (invited / joined, invited by, joined at), `weekly_tallies` (user, Monday, planned, done, streak; each person writes only their own). The first four can't be read or written directly: the app calls `gt_…` functions (`security definer`, empty search path) that check `auth.uid()`, and `gt_friend_records` returns a friend's days, split and sessions with notes removed. Only `gt_username_available` works signed out.

### 3.3 Offline-first sync

Every change is written to IndexedDB first (UI never waits on the network) and queued in an outbox in the same transaction. Sync runs after edits (debounced), on app open, on reconnect, and when the app comes back to the foreground: push the outbox (upsert), then pull rows changed since the last pull by server time (5-second overlap, paged), keeping whichever copy has the newer `updatedAt`. On a tie (same `updatedAt`, different contents) the copies decide, never the order they reached the server: the one holding more logged sets and done / skipped answers wins, then more note text, then a fixed order (`recordSync.settle`), and the winner's side uploads it again. After a pull that changed something, and at startup, `SetupService.reconcile()` files logs that synced in for merged or deleted exercises (D29). Settings (D20: theme, custom theme color, accent, custom accent color, the two recent-color lists, last session's numbers, Progress's lb / kg) are re-read on app open, back in front, sign-in and every Sync press; on window focus at most every 15 s (settings only, the status line doesn't change); otherwise at most once a minute. A value from another copy that this version can't read (a damaged copy, an id from a newer version) is skipped with its stamp instead of replacing a good one (D44). Session ids are deterministic (`<workoutDayId>:<date>`), so logging the same day on two devices edits one record instead of creating duplicates.

| Concern | Choice | Why |

| Build | **Vite** | Fast dev server, static build for Pages |

### 4.2 Layers and rules of the road

```
src/
  domain/      Entities + value objects: LocalDate, SetEntry, Exercise, WorkoutDay, Split,
               ExerciseLog, Session, DayStatus; social/ (Username, Profile, WeekTally, Room, SocialOverview).
               Pure TS, immutable, no I/O.
  services/    Use cases: SetupService, SessionService, CalendarService, ProgressService,
               ImportService, BackupService, SettingsService, SocialService. ports.ts = the interfaces they need
               (Repositories, SyncController, SocialGateway…).
  data/        RecordStore interface + IndexedDbRecordStore / MemoryRecordStore,
               StoreRepositories (implements the ports once, for any store), SupabaseSync, NoSync,
               SocialGateway implementations: SupabaseSocial (the gt_ functions), MemorySocialServer
               (the same rules in memory, for tests and ?demo), NoSocial.
  importers/   Grid, cell parsers, SheetImporter interface, MonthGridImporter, readWorkbook.
  app/         AppServices (composition root: the only place that picks implementations), demo data.
  ui/          React: Shell, router (hash routes), ServicesContext hooks, screens/, components/,
               theme/ (tokens.css, base.css, app.css, look.css; look.ts = the look's color math, pure),
               LookSync (applies the look to <html>), motion.ts, pageLayout.ts (centered pages, holds).
```

- Dependencies point inward: `ui → services → domain`; `data` implements `services/ports.ts`.
- `domain/` and `services/` never import React, the DOM, IndexedDB, or Supabase.
- Patterns in use: repository (ports + StoreRepositories), strategy (SheetImporter, RecordStore, SyncController, SocialGateway), observer (Emitter / ChangeFeed → `useLive` re-renders on any data change; `useRemote` does the same for server data such as Social, with an error state and a reload when the app comes back to the front), composition root (AppServices).
- New feature = new service (+ port if it needs storage) + screens. Screens never touch storage directly.
- `?demo` swaps in a MemoryRecordStore with generated sample data, so screens can be tried without real data.

### 5.3 Design lessons learned

Carried over from Catan Pangea:

- iPhone browsers can't use the Fullscreen API; the app-like view comes from the installed PWA (`display: standalone`), so show an "Add to Home Screen" tip on iPhone.
- Don't show install prompts on computers (mouse/trackpad as main pointer).
- Verify layouts at real iPhone sizes (~393 × 852), not only desktop.

From this project:

- **Name state classes `is-…`.** A row's `.empty` modifier picked up the global `.empty` empty-state padding and tripled the row height.
- **Dense lines need no dots.** With weekly points over 6 months on a phone, 8 px dots with a background ring made lines look dashed; dots now show only when there's room (hover still shows them).
- **Smooth lines can lie.** Curved interpolation overshot flat steps (weight looked like it dipped); use monotone interpolation.
- **Supabase free projects can't edit auth emails without custom SMTP** (checked 2026-11-21): the template page says "Set up custom SMTP to edit templates", and the built-in sender only delivers to organization members. Don't design a sign-in flow around custom email text until SMTP exists.
- **Inputs don't inherit muted label colors.** A day-name input inside a gray `<label>` rendered gray (inputs inherit `color` here), so `.field` sets its own text color.
- **Equal gaps need equal tracks.** Right-aligned Reps next to a left-aligned Last time column looked cramped no matter the gap; centering every data column in same-width tracks fixed it.
- **Inline label parts run together.** "Year the sheet starts in" and its hint were two `<span>`s, which rendered as one line ("…starts inGuessed…"). `.setting .text > *` is now `display: block`.
- **An inline-block dot sits on the text baseline.** In a 7 px slot it overflowed ~10 px downward onto the picked day's border; a grid slot centers it.
- **Don't slide the buttons.** Sliding the whole workout screen on a day change moved the ‹ › arrows under a quick second tap, which then hit the other arrow. Only the content below the header slides now.
- **Draw structure before data.** A screen whose layout depends on loaded data flashes and reflows on every visit; render what doesn't need data (the calendar grid) right away.
- **Name keys can collide.** "Leg press" and "Legpress" share the key `legpress`, so key-based matching treats them as one exercise already; tests need names with distinct keys.
- **Cached is not current.** Showing a screen's last data at once (D26) is fine for content, but an empty or "gone" screen drawn from an old copy is wrong, not just late; those wait for fresh data (D30). And "the previous value to keep showing" must be the last value *shown*, cached copies included, or quick double steps flip back to an older week.
- **Reserve space for anything that shows up after the first paint.** Inside a centered block it moves everything (D32).
- **Delayed cues need a timer.** `transition-delay` doesn't apply on an element's first render, and Reduce Motion's global `animation: none` also removes a delayed animation's end state; a JS timer plus a data attribute works in both cases.
- **An async step must check it's still wanted.** The screen may be gone when the lookup answers.
- **Positions keyed by history depth go stale.** A push discards the forward entries, and a page already at the top fires no scroll event.
- **Store the unit with the number.** A unit kept only on the parent re-reads all history when it changes (D28). Set units before merging: two names in one unit become one log per shared day.
- **Keep a choice where it can't be undone by a stale copy.** "Keep those in pounds" stamped on each log was undone by any device that re-saved an old session before hearing of the switch; on the exercise (the day record, which wins with the switch) it holds. "Those were plates" is kept on both the exercise and the logs, for the same reason. And only weights have a unit: a unit on a note-only log outlived the switch it predated.
- **Deletes and merges need tombstones in a last-write-wins sync.** Otherwise a record written offline can point at an id that no longer exists anywhere (D29).
- **A background repair must not be dated now, nor written blindly.** With whole-record newest-wins sync it overwrites a newer edit still on another device; date it just after the copy it fixed, write it only if that copy is still the stored one (a save can land between its read and its write), and settle equal stamps by the copies' contents, not by which reached the server last.
- **Update every device before switching units or merging across units.** Builds before v0.3.0 rebuild logs from known fields only, so re-saving a session there drops each log's unit until that device updates (the PWA updates itself on the next open).
- **Don't trust another device's clock.** A stamp copied from a device with a fast clock is in this device's future; stamp local changes at `max(now, previous + 1 ms)`, and treat a negative elapsed time as expired in throttles.
- **Last-write-wins on a whole object loses fields.** When fields change independently (settings), merge field by field (D20).
- **auth-js events aren't sign-ins.** `SIGNED_IN` fires on every tab return, `TOKEN_REFRESHED` about hourly, `USER_UPDATED` after every `updateUser`; reset sign-in state only when the user id changes.
- **A window that stays visible gets no `visibilitychange`.** Using the phone next to an open desktop browser only fires `focus` when you come back.
- **Rounding in a converter matters once its results are stored:** `platesToPounds(0.07)` was `7.000000000000001`.
- **Everything the user sets must follow them across devices** (the user's general rule, 2026-11-22): a new preference goes through SettingsService (synced per setting), new data through the synced record tables.
- **A shown value derived from another setting is derived when read, not stored.** Equal epoch stamps with different values make every device "apply" again on each sync (D34).
- **Custom properties resolve where they're declared and inherit as values.** Tokens built from `--accent` must be declared wherever `--accent` changes (each `data-family` element), or previews inherit `<html>`'s. `initial` on a custom property makes `var()` use its fallback.
- **Check contrast on the rounded hex values the tokens hold:** 2.99:1 slipped through on unrounded math. And check text on every ground it can land on — tints over panels and tiles included, not only the page background.
- **A clamp justified by one goal should be tested against that goal**, or it quietly over-corrects (the first custom accent rule recolored the user's button to keep text readable; now only the text color moves, D35).
- **A size container (`container-type: inline-size`) can't take its width from its content**; give it `width: 100%`. Container queries and transforms both become the containing block of `position: fixed` children — keep sheets out of them (portal to `<body>`).
- **A media-query override placed before its base rule of equal specificity silently loses.** Keep desktop overrides after the base rule (a test checks `.page`).
- **Centering the whole page means any height change moves every control:** hold the page while you interact, then glide (D41). Don't start a hold in the same commit the content first appears.
- **iPhone Safari applies `:active` only when something listens for touches**; the Shell adds a passive `touchstart` listener on the document.
- **A module-level preview needs an unmount cleanup in its owner**, not just a close handler: Back unmounts the picker without Cancel.
- **A click after a drag lands on the common ancestor** when mousedown and mouseup hit different elements, so "click on the backdrop" isn't "tap outside" (D37).
- **A hidden or background browser tab runs no ResizeObserver, requestAnimationFrame or CSS animations:** check layout there with getBoundingClientRect, not screenshots. Parallel agents each need their own tab and their own dev-server port (localStorage is per origin).
- **A button centers its content vertically.** Month tiles that became buttons put five-week months lower than six-week ones on the same row; a top-aligned column fixes it.
- **A transformed element counts toward its scroll container's scrollable area.** A scrolling overlay grew a scrollbar while its dialog animated in from elsewhere and shifted sideways by half of one; let the dialog scroll itself.
- **Layered dismissal without a shared stack:** give "outside" its own childless element (a click hits it only when the press started and ended there), keep the upper layer a sibling in the React tree (React events bubble through portals by the React tree, not the DOM), and have the lower layer stop listening for Escape while one is above it. Listeners added during an event aren't called for that event, so one press can't close two layers.
- **base.css's Reduce Motion switch is CSS only.** Web Animations started from code need their own `prefersReducedMotion()` check (`play()` has it).
- **iOS honours `preventDefault` on `touchmove` only from a non-passive listener registered before the touch starts:** add it to the list at mount, not at drag start. Give swipe surfaces `touch-action: pan-y`.
- **A click after a drag can't be stopped from the grip:** catch it in the capture phase on the list, and only clicks with `detail > 0`, so Enter and Space still work.
- **Drag offsets written straight to elements must be cleared in the same commit that renders the new order**, or the old order flashes for a frame. And when React reorders the list, the focused item can lose focus; put it back after a keyboard move.
- **A sync pull without its own `user_id` filter trusts row-level security to scope it.** Fine for one user; the moment anything shares rows (friends), it would download them. Pull `.eq("user_id", me)` and keep cross-account reads in functions that check who's asking (D53).
- **Test SQL against real Postgres in-process:** `@electric-sql/pglite` runs the migration with the `anon` / `authenticated` roles, RLS and a stand-in `auth.uid()`, so who-can-see-what is a unit test (`tests/sql-social.test.ts`, 70 cases). It caught an owner handoff by request time instead of join time and invited members' scores showing.
- **Keep the in-memory gateway's rules identical to the SQL** and run the service tests against it; when a SQL rule changes, change `MemorySocialServer` and add a test on both sides.
- **Demo data that has two sources must agree:** sample friends' scores are worked out from their sample workouts with the same code the app publishes with, or the card and its week dots disagree.
- **A timer stores times, not ticks:** iOS suspends a backgrounded PWA's JavaScript, so anything counted with `setInterval` stops; keep `startedAt` + counted time and work the face out from the clock. A web app can't ring while the phone is locked (that needs push), and iPhones don't vibrate from the web.
- **Testing tips:** headless Chrome/Brave won't make a window narrower than ~500 px, so screenshot phone layouts inside a 393 px iframe or the browser pane's mobile viewport; `--virtual-time-budget` screenshots don't wait for lazy-loaded chunks. Screens can be tested without a browser: `renderToString` renders the first frame from a cache filled with `prefetchLive` (no effects run), and `tests/screens-effects.test.ts` mounts with react-dom on a small stand-in DOM for effects (`tap()` and `pressKey()` there go through React's real listeners, so propagation and layered closing are tested, not just a handler's props). `SupabaseSync` is unit-tested with `vi.mock('@supabase/supabase-js')` (see `tests/preferenceSync.test.ts`); multi-device sync with the stand-in server in `tests/services.test.ts`. A screen that reads token colors at render (Progress's series colors) needs `document` and `getComputedStyle` stubbed for `renderToString` (`vi.stubGlobal`, undone in `afterEach`).

## 6. Google Sheets import

Download the sheet (File → Download → Microsoft Excel), then Settings → Import. Parsed on the device, previewed, then saved. Re-importing updates the same days/dates.

Rules (`MonthGridImporter`):

- **Dates:** the sheet only has "month, week N". Week N = the Nth Monday of the month onward; each session lands on its workout day's weekday from the chips in the preview (default guess: Upper 1 Mon, Lower Tue, Upper 2 Thu). Days with no weekday (Abs/Cardio) go on rest days in order. **Imported dates are approximate.** Year guessed from the sheet; months after December roll over.
- **Reps Google turned into dates** are decoded back: `9/9` → Sep 9 (this year) → 9/9; `8/7/7` → Aug 7 2007 → 8/7/7.
- **Weights:** `72.5/65` per set; one weight applies to all sets; `25 lbs` ok; `Body Weight` = bodyweight; text like `35(down)`, `No straps`, `7ish?` is kept as that day's note.
- **A weight with no reps is treated as planned, not done** (the sheet pre-fills weights). 41 such rows in the real export.
- **Copied weeks:** a week identical to the week before for the same day is skipped by default (24 in the real export).
- **Exercises:** matched by name key; the latest week decides what's active, older names become archived (kept for history). `(n)` in a name sets target sets. Names you renamed or merged in the app are aliases, so a re-import lands their rows on the exercise you kept (D25). Each name's rows are read in the unit that name was logged in, and rows on one date that land on one exercise combine into one log: its own names first, then merged names in the order they were merged (D28). A row without weights (a note alone) follows the exercise's unit. An exercise you deleted comes back as a new exercise if the sheet still has it.
- **Cardio rows** (`Cardio 1`, `Cardio 2`) become one done / not-done "Cardio" exercise; each starts a new Abs/Cardio session.

Real export result (2026-11-21): Upper 1 21 sessions, Lower 22, Upper 2 15, Abs/Cardio 5 (Feb 2 – Oct 20, 2026).
